# First saved website change

WEIR's next capability is to show a proposed website change, obtain the owner's approval and prove that the site saved it. A title correction in a private copy of Mission Control gives engineering a test case with a destination it can restart and inspect. The owner can choose a real job when they need one.

**Proposed operation.** Rename one manually managed task that the operator created in their Mission Control workspace. The site should save exactly the title displayed at approval. The same owner can reopen the decision in a later session after the job and browser close. This design enrolls no account or task. Live website changes are disabled.

**Platforms.** The proposed destination and trusted site connector run on Linux on `lugos-host`. The owner can review the proposal from a normal signed-in Mission Control client. The proof below used the installed Linux application in a private network namespace. It required no Windows service browser.

The implemented rehearsal uses a dedicated Mission Control task and a fresh database. It exercises the owner screen, two signatures, a single commit, independent verification, withdrawal and undo. A normal workspace task still requires enrollment and delivery qualification. [Run the private workflow](private-saved-task.md)

## What the destination actually does

The current task update checks the signed-in role and workspace. A title update also sets the task's modification time, records activity, broadcasts a task update and calls outbound sync. Depending on the installation, subscribers can receive the full task and matching events can reach webhooks, GitHub or GNAP. The write predicate uses the task ID and workspace. It has no expected task revision or destination command receipt. [Task route](https://github.com/mdn87/mission-control/blob/f2ec9dac2024ae42cf6610baa17fd819361895f8/src/app/api/tasks/%5Bid%5D/route.ts) · [Outbound sync](https://github.com/mdn87/mission-control/blob/f2ec9dac2024ae42cf6610baa17fd819361895f8/src/lib/github-sync-engine.ts) · [Webhook delivery](https://github.com/mdn87/mission-control/blob/f2ec9dac2024ae42cf6610baa17fd819361895f8/src/lib/webhooks.ts)

The task-detail GET can reconcile a pending completion before it returns. Moving a task into Review also makes it eligible for the automatic reviewer in a shared workspace. The reviewer can advance its status again. These behaviors make a title correction the simpler first operation and require a separate, read-only source for verification. [Deferred completion and automatic review](https://github.com/mdn87/mission-control/blob/f2ec9dac2024ae42cf6610baa17fd819361895f8/src/lib/task-dispatch.ts)

In a disposable instance, a signed-in operator changed a title and moved a different task into Review. A viewer received HTTP 403 for each attempted edit. A separate read-only SQLite connection confirmed that both edits survived a server restart. Restoring each original field left both activity records in place. The tasks were unassigned, and the test observed zero new task notifications. The fixture had only loopback networking. The status change and database witness characterize the ordinary destination. Delivery still needs all the acceptance tests below, including verification through an authenticated read-only site interface. ## What the owner would approve

| Item | Rule for the first saved title |
| --- | --- |
| Account and object | Mission Control verifies the approved human session and binds the immutable deployment, tenant, workspace, human actor, task ID and task generation. The task must still belong to this operator under destination-owned authorization, be manually managed and have no connected issue, assignee or pending automation. |
| Requested edit | The private approval view shows the workspace and task identifier, the exact old and new titles, the expected task revision and the recipients. Both titles must round-trip through the destination's validation and storage exactly. Refuse empty, identical, over-limit or ambiguously displayed titles. Treat titles as untrusted text and render them literally. |
| Allowed effects | One title replacement with its revision and modification time, plus one owner-only command receipt. The receipt is the private audit record. It creates no workspace activity-feed entry or activity webhook. Existing authorized workspace readers may see the current title on a later read. Pushed copies, notifications, status changes, reviewer dispatch and external sync are outside the decision. |
| Who may act | The signed-in owner must approve the displayed change with a fresh passkey. The decision covers the canonical operation, before and after values, version, site and account bindings, delivery policy, run, expiry and one-use budget. Fade issues the corresponding permit. WEIR verifies the signed decision and exact permit independently. |
| What can be reversed | The owner can request a second, separately approved change back to the original title. Both decisions and owner-only command receipts remain in history. Disclose that other authorized readers may already have seen the title. |

Treat this as an external submission with mandatory owner approval. Bind a versioned, title-only operation identifier into the decision. The operator's readable username and existing task `created_by` text cannot establish ownership across account renames or recreation. Mission Control must attest the stable owner or deny enrollment. Accept only well-formed NFC text of 1–500 UTF-16 units with no leading or trailing whitespace, control characters, line or paragraph separators, default-ignorable code points or lone surrogates. Reject input that trimming or normalization would change. Compare Unicode scalar sequences exactly. Display, sign and store the same UTF-8 text without later normalization. [Task validation](https://github.com/mdn87/mission-control/blob/f2ec9dac2024ae42cf6610baa17fd819361895f8/src/lib/validation.ts)

Task titles, the old value and source evidence inherit the workspace's personal or internal classification. Restricted content is ineligible for the first operation. Keep exact values in the owner-scoped evidence store for its configured retention period. Shared telemetry carries opaque references and outcomes. Neither the browser nor the effect worker receives the owner's reusable account credentials. The destination verifies the constrained service identity as well as the human decision.

The existing passkey rehearsal grants one unsaved marker fill on an enrolled inert page. Its fixed operation, value and credential scope cannot authorize a saved task edit. The new operation requires an explicit destination contract, grant and later deployment decision. Enrollment and a saved report carry no execution authority. [Unsaved field policy](production-effect-policy.md) · [Linux field qualification](acceptance/linux-enrolled-fill-20261122.md)

## Commit once and verify separately

1. **Read.** Mission Control supplies an authenticated, side-effect-free projection of the task, owner, workspace, eligibility, immutable generation and monotonic revision. Every task writer advances the revision in its transaction, including ordinary edits, deferred reconciliation, automatic reviews and inbound sync. A recreated task gets a new generation. An integer-second timestamp cannot distinguish an edit followed by its reversal.
2. **Review.** The private view displays both titles and allowed delivery. Mission Control is the WebAuthn relying party. Enrollment pins the exact HTTPS origin, its hostname as the RP ID and a registered credential for the stable tenant, workspace and human. Use its existing random, single-use challenge bound server-side to that identity, the distinct saved-title purpose and the digest of the canonical displayed decision. Require user verification. The challenge lasts at most five minutes and the resulting step-up grant at most 60 seconds. The signed decision capsule lasts at most 120 seconds. Bind the capsule and the Fade permit to the same command and display digest. No live RP or signing key is commissioned here. [Mission Control passkeys](https://github.com/mdn87/mission-control/blob/f2ec9dac2024ae42cf6610baa17fd819361895f8/src/lib/webauthn/remote-passkeys.ts) · [WEIR decision capsule](remote-decision-contract.md)
3. **Commit.** A dedicated destination operation verifies the independently signed human decision and Fade permit, their issuers, audiences and binding to the same job, command, versioned operation, data class and display digest. At commit it checks expiry, revocation, the unspent one-use budget, authenticated actor, tenant, workspace, task generation, expected revision, eligibility and delivery policy together. The destination serializes withdrawal against commit. It atomically stores the new title and revision, consumes the grant and writes the owner-only command receipt. A competing decision for the same revision fails. A different digest under the same deployment, tenant and command ID is a conflict.
4. **Recover.** After response loss or interruption, read the stored outcome. A duplicate of a completed command returns its receipt. A missing row is unknown while a valid request could still arrive. A terminal cancellation must atomically fence that command and grant at the destination so an in-flight request cannot subsequently commit. Expiry must also be checked inside the commit transaction. A withdrawal after a commit requires reconciliation. Unresolved dispatch leaves the grant spent and the task suspended for further writes. Retain receipt digests, unused-command cancellation records and spent-grant markers through the longest replay and reconciliation period, and for the life of any reopenable decision. Purging protected title text cannot rearm authority.
5. **Verify.** A separately authenticated, read-only destination path reads the committed result and revision and, where available, the current field value. Bind the actor, command, object, before and after evidence, destination revision and time to the originating job. If another edit has followed, report the historical committed result and the later state separately. Limit the public projection to opaque identifiers and outcome. Recheck the same human's current tenant and workspace access whenever they reopen protected history.
6. **Reverse.** A rollback is a new explicit decision with fresh source evidence, its own command ID and one-use grant. Compare against the version produced by the original command. If another actor has edited, moved or replaced the task, refuse the automatic reversal. A restart or a failed verification cannot silently restore a title.

The general task PUT and task-detail GET do not meet these rules. The site-owned operation must account for deferred consumers of the updated revision or timestamp, including queues, scheduled sync, digests and exports. The delivery rule must survive restart and follow the change through each consumer. Deny enrollment where that property cannot be demonstrated. Turning off integrations globally or changing other users' workspace settings is outside the approval.

## Acceptance before enrollment

| Case | Required result in the private destination |
| --- | --- |
| One approved correction | One owner-only command receipt, the correct task and title after restart, and a verified result in the original job. Other accounts cannot reopen the private decision. |
| Immediate and delayed delivery | Exercise reachable synthetic SSE, webhook, GitHub, GNAP, notification and reviewer receivers with positive controls appropriate to each channel. After the approved edit, prove zero prohibited deliveries, including queued work across restart and at least one full applicable scheduler and sync interval. |
| Declined, expired or withdrawn | The old value survives. The owner sees the terminal decision. A delayed request cannot commit after a cancellation fence or expiry. |
| Wrong scope, signature, human or displayed decision | A different person's valid passkey, changed display digest, wrong tenant, workspace, target, generation, operation or title all yield zero writes. The verification reader cannot write. The effect identity cannot use the general PUT or change another task or its status. An effect identity without the signed human decision is insufficient. |
| Races across task writers | An intervening ordinary edit, reconciliation, reviewer or sync update makes the expected revision stale. Changing the title back or recreating the task cannot revive approval. Two concurrent requests for one version yield at most one commit. |
| Title fidelity | Check valid NFC, a decomposed equivalent, trailing spaces, a zero-width joiner, lone surrogates and the 500/501 UTF-16-unit boundary. The approved, persisted and independently read bytes agree. |
| Lost response or crash | A status read distinguishes a committed receipt, terminal fenced absence and unknown. Reopening and replay never create another change or receipt. |
| Restoration | A fresh approval bound to the original post-write revision restores the title once and creates its own owner-only command receipt. A later edit causes a terminal refusal visible to the owner, leaves the later value intact and voids the reversal grant. |

These are delivery tests for the saved-change chip. The private characterization covers the ordinary destination today. The reviewed unsaved live canary and an explicit decision to commission the new saved operation are still required before a real operator task can be changed.
